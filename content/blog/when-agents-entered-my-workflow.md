> 这不是一篇严谨的产品横评，也不是“2026 年最强 coding agent 排名”。它只是我在第一次实习期间，陆续使用 Cursor、Codex、Hermes、OpenCode、Claude Code、Pi，以及接触 ClawChat、Paseo 后留下的一份主观使用手记。
>
> 很多感受只适用于我当时的模型、接入方式、预算和工作类型。对我来说，重要的也不是找到一个能替代所有人的 Agent，而是慢慢弄明白：不同的 harness 应该被放在工作流的什么位置。

## Cursor：我最早意识到“项目可以这样做”

我最早真正使用 coding agent，其实是 Cursor。

那是在 2024 年。当时 Copilot 对我来说还是 VS Code 里的一个插件，能用的 Agent 也没有现在这么多。为了小学期集中实习的项目，我甚至在闲鱼上买过一个便宜的 Cursor 续费。

第一次使用时的具体细节已经记不太清了，但有一个感受到现在还在：**如果没有 Cursor，我们那个项目大概率完成不了。**

现在回头看，这句话多少有一点夸张，也可能是当时第一次接触这种能力带来的震撼。但在那时，它确实让我第一次感到：写项目不一定只能靠自己在搜索引擎、文档、报错信息和代码文件之间来回切换；原来可以有一个东西跟着项目上下文，一起讨论、补代码、改问题。

第二次更深地使用 Cursor，是做毕业设计的时候。

它自带 IDE，和 VS Code 的迁移成本很低；我的项目需要跑在服务器上，而 Cursor 的 SSH 使用体验让我印象很好。能直接连到远程环境，在相近的编辑器界面中处理项目，不需要为了“在服务器上写代码”额外折腾很多部署、同步和切换，对当时的我来说很舒服。

如果现在想从命令行安装 Cursor CLI，官方给出的入口是：

```bash
curl https://cursor.com/install -fsS | bash
```

而如果需要的是当年那种完整 IDE + SSH 的体验，直接从 [Cursor Download](https://cursor.com/download) 安装桌面端更合适。安装后可在命令面板执行 **Install `cursor` command in PATH**，以后可以从项目目录直接打开：

```bash
cursor .
```

不过，我后来也意识到另一件事：**能把项目做出来，不等于真的把项目做好了。**

那时的我基本属于纯 vibe coding。项目和论文都借助了很多 AI 生成内容，但我对模型是什么、资料从哪里来、引用是否真实、语言是否准确，并没有建立足够的审查意识。最后回看，论文中存在引用不够可靠、表达质量不够好的问题。

而且我一直使用的是 Cursor 的 `Auto` 模式，甚至不知道背后实际调用的是什么模型。

我会用 Cursor，但我不理解 Agent；我得到了结果，但说不清结果是怎么来的。这个认知空白，在后来实习面试时突然变得很具体。

## 一场面试，让我第一次开始了解 harness

第一次实习面试时，面试官问我现在使用什么编程 Agent。

我回答：Cursor。

他接着问：那你用的是什么模型？

我才意识到，自己一直都在用 `Auto`。除了“我用过 Cursor”，我几乎不了解 Agent，也不了解当时的大模型生态。后来他又问到 Skill、MCP 等概念，我更是一问三不知。

当时我对 Agent 的理解，大概可以写成这样：

```text
Agent = LLM + 提示词 + Tool +（记忆）
```

现在看，这个公式不算完全错误，但它实在太简化了。

后面我慢慢接触到，真正决定一个 Agent 能不能进入工作流的，不只是模型和提示词，还包括：

- 它如何拿到项目和对话上下文；
- 它能调用哪些工具；
- 工具调用是否可见、可审查、可中断；
- 它如何保存记忆、加载规则、复用经验；
- 它如何处理权限、文件修改、终端命令和失败反馈；
- 多个 Agent 或多个会话之间，任务和上下文如何隔离。

也就是后来我经常听到的那个词：**harness**。

我现在更愿意把 harness 理解成一层工作台：它把模型、终端、代码库、文件、浏览器、上下文、记忆、权限和协作方式组织到一起。模型决定它“会不会想”，harness 则很大程度决定它“怎么做事、能做什么、以及我能不能控制它”。

第一次实习前几天，我其实有点惴惴不安。

我怕自己什么都不知道，于是努力回忆面试里没答上的问题，在 B 站和与 AI 的对话中集中恶补了一遍。可看着 Agent、MCP、Skill、RAG、Tool Calling 这些一个个概念，我常常有一种很奇怪的感觉：好像理解了，又好像完全不知道它们具体能做什么。

刚好那段时间，B 站的推荐机制也开始发力：我刷到的几乎全是“Codex + 某某工作流”“推荐一些 Skill”“如何把 Agent 接进开发流程”之类的视频。与此同时，同学也给我推过面向 Codex 的中转接入方案，包括一批 Sub2API 一类的服务、配置导入和兼容 Claude Code 的路径。

于是，Codex 理所当然地成了我的下一个入口。

## Codex：足够强大，但工作流也有成本

当时我接入 Codex 的方式并不算便宜。

即使是通过中转使用 GPT-5.5，轻度使用下来也大约要一天 10 元。后来才发现，里面还有一部分是我自己分组用错了。对一个还在实习、刚开始摸索 Agent 的人来说，这种成本会让每一次调用都带一点心理负担。

但从能力上说，Codex 已经足够强大。

它能完成我期待中的 vibe coding：围绕一个需求生成和修改项目代码；也能进入更完整的开发闭环，例如结合浏览器检查页面、对具体位置提出不足后继续修改，或者参与 Git 审查。

我后来用 Codex vibe 开发过自己的博客网页。真正让我感到舒服的，不是它“能一下子生成很多代码”，而是它可以在一个相对连续的循环里工作：

```text
提出目标
  ↓
阅读项目与现有代码
  ↓
修改实现
  ↓
启动或检查页面
  ↓
根据问题继续调整
  ↓
查看 diff / 审查改动
```

这种“做出来—看一眼—指出问题—继续改”的闭环，比单独把代码复制到聊天框里问“这样对不对”自然得多。

如果只是想快速体验官方 Codex CLI，当前文档提供了安装脚本：

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

也可以通过 npm 安装：

```bash
npm install -g @openai/codex
```

但命令只是入口。真正的体验还取决于模型、账号套餐、项目权限、浏览器工具、网络和 harness 本身。

后来 DeepSeek 也发布过“适配 Codex”之类的说法。我的实际感受是：**接口能接上，不代表模型真正适配了 Codex 的工作流。**

这不是说模型不能回答，也不是说协议兼容没有意义。问题在于，一个 harness 对模型的要求远不止“返回一段文本”：它还要求模型在合适的时候调用工具、遵守阶段、理解上下文、在完成后汇报而不是无限扩展任务。能用 API 接入，只是第一层；能稳定地在原生工作流中工作，才是另一层。

可惜的是，Codex 最完整的体验还是在 GPT 生态下。对当时的我来说，资金有限，这使得它很难成为唯一的长期主力。

## Hermes：我真正开始“养马”的地方

后来进项目组，有人让我学一下 Hermes。

从那以后，Hermes 成了我研究和工作的主力之一，也是我真正开始“养马”的阶段。

我这里说的“养马”，不是指让 Agent 莫名其妙地自我进化。更接近的意思是：我开始给它补充规则、积累经验、总结流程，然后观察它在后续任务里是否能更稳定地复用这些东西。

在 Hermes 里，我第一次把之前背过的概念真正用起来：

- **Skill**：把重复任务沉淀成可复用的步骤和规范；
- **Memory**：保存长期有效的用户偏好、环境信息和经验；
- **MCP**：把外部能力接入 Agent；
- **worktree**：让多个代码任务在隔离的 Git 工作目录中进行；
- **profile**：为不同目标隔离配置、上下文、记忆和工具；
- **cron**：让一些重复整理工作不必每次手动发起；
- **Kanban / 多 Agent**：尝试把复杂任务拆分、分配和跟踪。

Hermes 官方的安装入口在类 Unix shell 中是：

```bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
```

安装完成后，至少可以先做三件事：选模型、检查环境、启动对话。

```bash
hermes setup
hermes doctor
hermes
```

在 Windows 原生环境中，安装和 PATH 是否生效可以用下面的 PowerShell 命令确认；如果输出的是 `hermes.exe` 的实际路径，说明命令已可用。

```powershell
Get-Command hermes
hermes --version
```

Hermes 的能力边界很宽：同一个核心可以跑在 CLI、桌面端、消息平台、不同模型提供方和多个 profile 上。它很适合被当成一个长期工作助手，而不是一次性的代码生成器。

例如，当前官方文档中可以用 profile 隔离不同 Agent：

```bash
# 查看已有 profile
hermes profile list

# 从当前配置克隆一个新的隔离 profile
hermes profile create research --clone
```

每个 profile 可以有独立的配置、技能、记忆、会话和定时任务。对我来说，这个隔离非常重要：不同任务的上下文不是越多越好，混在一起反而容易污染。

Hermes 的 cron 也让我第一次体会到：Agent 不一定非要“现在帮我写代码”。

我有一个定时任务，会整理每天的对话内容，写成实习日志，并提取其中涉及的知识点。它不是什么惊天动地的自动化，但很贴合真实工作：日常对话里很多信息当下看起来零碎，过几天再回忆就已经丢了；让它按周期归档、提炼，反而能慢慢积累成可回顾的材料。

```text
日常对话 / 项目讨论
        ↓
定时汇总
        ↓
实习日志
        ↓
知识点提取与复盘
        ↓
本地知识库中的长期材料
```

这也是我现在主要把 Hermes 放在学习、科研工作流设计和长期整理上的原因。

### 但长期使用后，Hermes 也让我感到“重”

Hermes 是一个很不错的工作助手，但我持续使用下来会觉得它有点“重”。

这里的“重”不是单指启动速度，也不是单指功能多，而是一整套长期维护成本：

- 自带和默认启用的 Skill 较多，每轮对话会携带完整的 Skill 列表及其元信息；
- 我一开始担心这会大量增加上下文消耗，后来了解到模型供应方的 prompt caching 机制，才知道这部分影响未必如我最初想的那么大；
- 但 memory 的自动沉淀在我的使用体验里偏宽松，Skill 中已经设计好的内容、或者并不值得长期保留的旧信息，也可能重复进入 memory；
- memory 很快就满了，我记得当时容量大约只有两千字节量级；
- 因此我开始拆 profile，按功能与上下文做隔离。

这让我开始认真区分三类东西：

```text
一次性上下文：这次任务结束就可以遗忘
长期事实：用户偏好、稳定环境、长期约束
可复用流程：应该沉淀为 Skill，而不是反复塞进 memory
```

这看起来像很小的整理工作，但实际上决定了一个长期 Agent 会越用越顺，还是越用越乱。

我也试用了 Hermes 的 Kanban 和多 Agent 协作能力。不过至少在我现在的工作里，我越来越觉得：**不是所有任务都需要多 Agent。**

很多任务的难点不是“人手不足”，而是上下文不清、验证不够、边界不明确。为了多 Agent 而多 Agent，可能只会多出通信和协调成本。对我来说，多 Agent 更像一个在任务确实足够大、可以明确拆分、且需要并行时才拿出来的选项，而不是默认答案。

### Gateway、桌面端和黑盒感

还有一些问题，至今我也没有完全定位。

Hermes 和 OpenClaw 都可以作为 gateway 类 Agent 来使用：同一个 Agent 可以经由不同入口服务消息平台、桌面端或其他表面。但我的 Hermes gateway 在做大任务时偶尔会崩溃，启动加载也偏慢，原因暂时没有找到。

这主要影响了我使用桌面端，所以后来我逐渐改用 CLI。习惯之后，CLI 其实很舒服：它更接近任务发生的地方，终端、文件、Git、命令输出都在附近。

但 Hermes 还有一个让我不太舒服的地方：**工具调用过程对我不够可见。**

我看不到足够详细的工具调用信息和原始输出。即使尝试打开相关显示，在报错、长工具执行、等待后台输出时，仍然会有明显的黑盒感。

对我而言，真正难受的不是“它自动做事”，而是我无法明确知道：

- 它现在正在调用什么；
- 命令的原始输出是什么；
- 失败发生在哪一步；
- 一个长任务到底还在执行、卡住，还是已经偏离目标；
- 我应该在哪个时机介入。

这一点也影响了我对不同模型的感受。

我看到有人说 DeepSeek 在 Hermes 里很有“干劲”，这个说法让我很有共鸣。但我的意思不是它特别勤奋，而是它有时**不太能被 harness 住**：指令遵循不够稳定，Skill 中已经写清楚的流程可能不按要求执行，需要我在对话里反复提醒；我本来希望它输出一份完整的工作报告，它却可能发现新的事以后继续自己工作起来。

模型会主动扩展任务，在某些场景当然是优点；但在我需要一个可审查、可预测、按流程交付的助手时，这就会变成问题。

## Pi：我需要的不是更花哨，而是更可控

最后，我把主力工作 Agent 逐渐迁移到了 Pi。

Pi 对我来说像一个“莫得感情的执行机器”。

这并不是贬义。相反，它正好符合我当时最需要的东西：轻量、可控、少一点系统替我做决定，多一点我能看见的过程。

Pi 的定位更接近一个由基础能力组合起来的 coding agent，而不是把所有工作流都预设好了的“大而全工作台”。它可以通过扩展和包来增加能力，也可以更贴近 CLI 的交互方式。

Pi Coding Agent 可以直接从 npm 安装：

```bash
npm install -g @mariozechner/pi-coding-agent
pi
```

它的一个很符合我个人偏好的地方，是可以明确收紧本次会话的内置工具范围。例如只留下读取和 shell 能力：

```bash
pi --tools read,bash
```

例如，Pi 的扩展包可以按 npm 或 Git 来源安装：

```bash
pi install npm:<package-name>
# 或
pi install git:github.com/<owner>/<repository>
```

但比安装命令更重要的是，它让我能更完整地看到模型的思维和执行过程。

在 Agent 做错时，我可以及时 steer；在它开始往错误方向走时，我可以打断；在工具调用失败时，我不必只等一个模糊的最终回答。

慢慢地，我形成了一个很个人的判断：

> 对我来说，能否及时接管和修正，有时比 Agent 能否自主跑得更远更重要。

Hermes 更适合我做长期沉淀、知识整理和工作流编排；Pi 则更像一个我愿意放在手边、随时观察和接管的执行器。它们不是简单的替代关系，而是不同的分工。

## Claude Code、OpenCode 与“并不是每个工具都要成为主力”

在这期间，我并不是只用了 Hermes 和 Pi。

### Claude Code：DeepSeek vibe coding 的下位替代

Claude Code 我也一直在用，但不是主力。

当前我的主要工作并不是传统意义上的研发：不是持续写业务代码，也不是每天修 Bug。即使需要开发，我可能也会更倾向于 Codex；而我这里使用 Claude Code 的一个实际背景是，它接入的是 DeepSeek。

我把它更多当作 DeepSeek vibe coding 的一个下位替代，并且给它接了专门的视觉 MCP，再让 GPT 负责图像理解能力。这样做的原因很直接：当任务涉及截图、页面、图表或视觉反馈时，模型的读图能力会直接影响后续代码修改质量。

Claude Code 当前可以通过官方安装方式启动，例如在 Windows 上：

```powershell
winget install Anthropic.ClaudeCode
claude
```

也可以通过 npm 安装：

```bash
npm install -g @anthropic-ai/claude-code
```

但我现在不会因为一个工具“很强”就强行把它变成主力。工具是否适合我，取决于它能否进入我正在做的任务，而不是它在网上的评价有多高。

### OpenCode：一次很夸张的环境事故

我也试过 OpenCode。

它是一个更强调 provider-agnostic 的终端 coding agent。当前最直接的安装方式是：

```bash
npm install -g opencode-ai
opencode --version
opencode auth login
```

如果只想跑一个有边界的任务而不进入完整交互界面，也可以使用：

```bash
opencode run "先阅读当前仓库；只报告问题和建议，不修改文件"
```

不过第一天，它就把我的用户级 `PATH` 清掉了。这个事故很夸张，也直接让我没有继续深入体验。

我不会据此下结论，说 OpenCode 对所有人都不可靠。它只是我在自己的环境里遇到的一次严重事故。但它提醒了我一件很朴素的事：

> Agent 能改系统环境时，能力和风险是同一件事的两面。

尤其是涉及用户级环境变量、包管理器、shell 配置、全局路径或系统配置时，自动化之前最好有备份、diff、确认和可回滚方案。Agent 不是不能做这些事，而是这类任务不应该被当成普通文本生成。

我后来会把“只读摸底”和“允许修改”分成两步。第一步先固定 Agent 的边界：

```text
先检查当前项目与环境；不要修改任何文件、环境变量或全局配置。
请报告：你准备执行的命令、风险点、建议的备份或回滚方式。
等待我确认后再动手。
```

这不能从根本上消除风险，但至少能让“先看清楚再授权”成为默认动作。

## ClawChat 和 Paseo：Agent 开始不只是一个终端窗口

ClawChat 对我来说，目前更像一个“没什么用、但还算有趣的玩具”。

它让我接触到另一种想象：Agent 不一定只能待在本地终端或一个网页聊天框里，它也可以拥有身份、联系人、群组、消息入口和互动关系。现在它对我更多还是好玩，而不是生产力工具；但它至少让我看到，Agent 的下一层问题可能不再只是“会不会写代码”，而是“如何在真实通信关系里协作”。

Paseo 则更贴近我实际会用到的东西。

它能把多个 Agent 的 CLI 对话聚合到一个界面中，保留流式输出；而且它有移动端，可以让我离开电脑后仍然接着处理事情。我现在也会把它当成 Pi 的桌面端/跨设备入口。

Paseo 的价值，对我来说不只是“多 Agent 协同”这几个字。

我之前试用多 Agent 后已经发现：大多数任务未必需要多个 Agent 才能完成。但当我确实同时开着多个执行窗口，又希望看见每一个窗口正在做什么、随时切换和干预时，一个统一且保留流式过程的界面就很有用。

这和我在 Hermes 里感到黑盒不舒服，其实是同一件事的另一面：我越来越在意过程是不是可见，控制权是不是还在自己手里。

Paseo 的前提不是再造一套模型配置，而是本机至少已经有一个完成登录和配置的 Agent CLI。它再去调度这些原生 CLI，让既有的 Skills、MCP 与配置继续生效。若使用其 CLI / headless 入口，可以这样安装：

```bash
npm install -g @getpaseo/cli
paseo
```

至于 Trae、WorkBuddy 这类以桌面应用或网页/小程序为主的产品，我更建议直接从官方 [TRAE Download Center](https://www.trae.ai/download) 和 [WorkBuddy 官网](https://www.workbuddy.ai/) 进入，而不是为了凑齐命令行去找非官方安装脚本。它们对我而言也不是这篇文章的主力工具；更深入的配置、模型与工作流，读者可以沿各自官方文档继续探索。

我还短暂关注过 Grok Build。它属于终端型 coding agent，官方提供了下面的安装入口；我没有把它写成自己的主观主力体验，因此只把它留作读者自行试用的延伸：

```bash
# macOS / Linux / Git Bash
curl -fsSL https://x.ai/cli/install.sh | bash

# Windows PowerShell
irm https://x.ai/cli/install.ps1 | iex

grok --version
```

## 现在的分工：不找“最强”，而是找合适的位置

到现在，我不会再期待某一个 Agent 接管所有工作。

我大致形成了这样的分工：

| 工具 / 项目 | 我目前更愿意把它放在哪里 |
| --- | --- |
| Cursor | 我最早的 coding agent 记忆；熟悉 VS Code、远程 SSH 场景下体验仍然有吸引力 |
| Codex | 更完整的开发闭环、vibe coding、浏览器反馈与 Git 审查；但成本和 GPT 生态决定了实际使用门槛 |
| Hermes | 学习、科研工作流设计、长期上下文、profile 隔离、Skill / memory 沉淀、定时整理任务 |
| Pi | 轻量而可控的主力执行 Agent；便于观察过程、及时 steer |
| Claude Code | DeepSeek vibe coding 的补充入口；搭配视觉 MCP 处理读图与页面相关任务 |
| OpenCode | 有过一次环境事故，暂未成为常用工具 |
| ClawChat | 有趣的 Agent 通信/社交实验，目前更偏玩具 |
| Paseo | 多个 CLI Agent 的可见化界面、流式输出和移动端入口，也作为 Pi 的桌面端补充 |

如果要把这段实习期间的体验压缩成一句话，大概是：

> 我不再只问哪个 Agent 最强，而是开始问：这个任务需要什么上下文、多少自主性、怎样的可见性，以及我应该在什么时候接管它。

一开始我以为 Agent 的价值是“替我做事”。

后来我才慢慢意识到，真正要学习的是：如何给它划分上下文，如何把重复流程变成 Skill，如何避免记忆污染，如何让工具调用可见，如何限制权限，如何在它跑偏时及时介入，以及如何不把“它做出来了”误认为“我已经理解了”。

Cursor 让我第一次觉得项目可以被这样完成；面试让我意识到自己并不了解 Agent；Codex 把我带进 coding agent 的工作流；Hermes 让我开始养自己的工作台；Pi 则让我重新找回对执行过程的掌控感。

我现在还没有找到所谓“最强的 harness”。

但至少我开始知道：工具不是一段会自动完成工作的魔法。它是工作流的一部分。把它放对位置、看清它正在做什么、保留自己接管和判断的能力，可能比给所有 Agent 排一个总名次更重要。
